## 三个范式的本质差异

### ReAct
```
思考 → 行动 → 观察 → 思考 → 行动 → 观察 → 回答
```
- **优势**：灵活，LLM 自己判断需要什么信息，不浪费调用
- **劣势**：黑盒——你不知道它下一步要干什么
- **适合**：信息不确定的任务，需要边试边调整

### Plan-then-Execute
```
先列计划（纯文本，不调工具）→ 再按计划执行（调工具）
```
- **优势**：透明——用户能看到完整思路，可控性强
- **劣势**：计划可能过度详细（B 方式有 bug：计划文本里 "步骤" 出现 10 次导致多跑了 3 轮）
- **适合**：任务明确、步骤可预见的场景，如"对比三个产品"

### Reflexion
```
执行 → 产出答案 → 自我检查 → 发现不足 → 补充 → 最终答案
```
- **优势**：有质量保证——LLM 自己审一遍再交卷，类似"打草稿→检查→誊写"
- **劣势**：多一轮 API 调用，且反思质量取决于 LLM 自身能力
- **适合**：对答案质量要求高的场景，如报告、代码审查

## 本次实测发现的问题

1. **Plan-Execute-B 步数解析 bug**：用 `plan_text.count("步骤")` 计数，但计划文本本身包含"步骤"字样，导致计数偏大（10 而不是 5），多跑了 3 轮空步骤
2. **Plan-Execute 中 LLM 提前回答了**：在计划阶段 LLM 就习惯性地把执行细节和答案也一起输出了，导致后续步骤变成重复确认
3. **三个范式最终答案一致**：都认为 Agent 最相关，说明答案可信

## 一句话总结

| 范式 | 一句话 |
|------|--------|
| **ReAct** | 边想边做，方向盘交给 LLM |
| **Plan-Execute** | 先看地图再开车，路线透明 |
| **Reflexion** | 打完草稿自己检查一遍再交卷 |
